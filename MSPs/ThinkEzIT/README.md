## Proof-of-concept success hierarchy

The ThinkEzIT POC succeeds only if all three layers produce usable business value, in this order:

1. Automate ThinkEzIT operational workflows.
2. Build ThinkEzIT's internal AI-enabled MSP operating model.
3. Prove a commercial managed AI offering that ThinkEzIT can sell.

Technical completion alone is insufficient.

### Practical failure condition

If ThinkEzIT does not use what is built, cannot sell it, or the market will not buy it, the POC has failed regardless of technical elegance.

## Initial operating tracks

### Track 1 — Operational workflow automation

Prioritize high-friction, repeatable ThinkEzIT workflows where automation can measurably reduce cycle time, rework, manual entry, missed information, or handoff failures.

Known starting point: onsite evaluation -> structured capture -> quoting / downstream customer workflow.

### Track 2 — Internal AI-enabled MSP operating model

Create an AI operating layer that ThinkEzIT personnel will actually use in day-to-day MSP work. The model must fit ThinkEzIT's existing team, tools, customer relationships, security obligations, and operating style rather than impose an MJC-sized engineering model.

### Track 3 — Commercial managed AI offer

Package a governed managed-AI service that ThinkEzIT can explain, deliver, support, and sell to SMB customers. The offer should integrate cybersecurity, identity, data protection, governance, evidence, and Decision Assurance where those capabilities materially improve customer value.

## Agent architecture

ThinkEzIT gets one primary MSP AI agent: a tailored generalist capable of assisting across sales, discovery, assessments, documentation, operations, customer communication, cybersecurity, managed-AI governance, and workflow execution within its approved authority.

The agent should orchestrate tools and workflows, not imitate MJC's larger internal agent organization.

## Authority model

### May perform without owner confirmation

- Read authorized email, repository, Project, and approved library sources.
- Analyze workflows, documents, requirements, risks, and opportunities.
- Draft requirements, SOPs, runbooks, architecture, backlog items, decision records, assessments, and customer-facing material.
- Prepare repository branches and pull requests.
- Maintain project knowledge and traceability artifacts.

### Draft but do not independently send or approve

- External partner/customer communications unless specifically delegated.
- Material pricing or commercial terms.
- Public claims.

### Never autonomously perform

- Financial commitments.
- Contract acceptance.
- Legal approval.
- Destructive repository actions outside approved change control.
- Production publication or deployment without explicit authorization.

## Source-of-truth hierarchy

1. Approved repository artifact
2. Current explicit owner direction
3. Current email/source document
4. Project files and approved persistent library material
5. Memory/conversation context
6. Inference

Memory is an accelerator, not an authority.

## Evidence standard

For each material capability, capture:

- Problem being solved
- Current baseline
- Proposed change
- User/owner
- Expected measurable outcome
- Adoption evidence
- Commercial relevance
- Validation result
- Decision and follow-up

Do not label a capability successful because it was built. Confirm it was used, produced the intended operational result, or generated qualified commercial evidence.
